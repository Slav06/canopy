# Free testing deployment (current default)

The root `render.yaml` now uses only a Render Free Node web service. Create a Neon **Free** PostgreSQL project separately and supply its SSL connection URL as `DATABASE_URL` in Render's secure environment form. Neon Free currently has no time limit or required credit card, subject to free-plan usage limits. Render's free server sleeps after inactivity and can take about a minute to wake. Keep both accounts on Free, do not enable paid plans, and do not add a payment method for this test setup. If either provider requires payment to proceed, stop and review rather than activating it.

No Render database or persistent disk is created by this default profile. Agent accounts, leads, notes, appointments and other CRM records live in Neon. Local document/photo uploads are disabled in both the UI and API because Render Free storage disappears on restart. CSV imports still save records in PostgreSQL. Test with sample records first and export test data regularly; free hosting has limits and is not a permanent production reliability guarantee.

Steps: connect Render to the repo; create Neon Free project; paste DATABASE_URL directly into Render (never chat); deploy the root Blueprint. Startup creates the empty live workspace. Open the HTTPS address straight away, enter your name to claim Admin and save the private link shown, then create a private link for each agent under Team and assign test leads. No automatic paid upgrade is configured in the Blueprint.

Verified provider policies: https://render.com/docs/free and https://neon.com/pricing . No hosting resources have been provisioned yet.

# Deploy Canopy CRM to Render

This deploys the Node CRM directly from Slav06/canopy, with individual logins, a separate live PostgreSQL database and a persistent private file disk. Existing sample data on the Mac is not uploaded. No live deployment exists until Render provisioning and post-deployment checks complete.

## Resources to review before deploying

The optional render.production.yaml describes a Starter Node web service, Basic-256mb PostgreSQL with 1 GB storage, and a 1 GB private file disk in Ohio. These are PAID resources. Review current charges in Render before creating the Blueprint. No usage-based autoscaling is enabled. Provider bandwidth/build overages and taxes can still apply. The free Render Postgres plan expires and is unsuitable for permanent team data.

## One-time setup

1. Sign in to https://dashboard.render.com/ and select the intended workspace. Approve only the GitHub repository access needed for Slav06/canopy. If necessary, the repository owner must authorize the Render GitHub app for that repo.
2. Create a new Blueprint from https://github.com/Slav06/canopy using render.yaml. Review the selected services and costs before deployment.
3. There are no login credentials to set. SESSION_SECRET is generated by Render. Database connection uses Render's private network. The database external-IP allowlist is empty.
4. Render builds the app, then runs npm run start:live. Startup derives APP_ORIGIN from Render's HTTPS URL, applies idempotent schema creation before listening on Render's PORT. Existing accounts are never changed on redeploy.
5. When health checks pass, open the HTTPS service address. Confirm anonymous API access is refused, claim Admin by entering your name, save the private link shown, and verify the live banner/empty lead list. Create individual Basic Agent or Upper Management accounts under Team and assign their leads. Each agent opens their own private link; there are no emails or passwords. Until Admin is claimed, anyone who finds the address can claim it, so do it immediately.
6. Check a second account cannot access unassigned leads, export data or delete leads. Only Admin can delete/restore. Management capabilities begin disabled. Dialerr toolbar login/permissions are separate from CRM credentials. Configure vendor-side agent permissions before calling. No Dialerr data API is used.

Automatic deploys are disabled. Pushes update GitHub, then manually deploy after review. Render's persistent disk requires one service instance and can cause brief downtime during deployment. Never scale this configuration horizontally without shared private object storage.

## Persistence and recovery

CRM records use PostgreSQL. Private documents use CRM_DATA_DIR=/var/data/canopy. The same environment setting is used by backup/restore scripts. Paid database recovery and disk snapshots are provider features; also take encrypted full CRM backups including document bytes to a separate owner-approved destination. Restore only to a fresh empty workspace, and test recovery before substantial real data entry. No external backup destination is configured automatically.

## Provider integrations

Satellite/map embeds work without setup. Mapillary remains deferred. Google Calendar sync remains optional. Keep live calling flags false until a specifically authorized test and Dialerr agent permissions have been verified; those flags do not control provider-native toolbar actions. This deployment does not import or synchronize Dialerr's lead database. Import an owner-approved CSV into the CRM and assign leads to agent accounts.

## Health and troubleshooting

/api/health is intentionally public, returning only ok/unavailable and 200/503 based on database, session secret and active Admin readiness. It never returns records. /api/state requires authentication.

If startup fails, check Render logs for missing configuration or database reachability. Do not log credentials. If adding a custom domain, set APP_ORIGIN to its exact HTTPS origin and redeploy so origin protection remains correct. Disk backups and database recovery are separate from GitHub source history.
