# Deploy Canopy CRM to Render

This deploys the Node CRM directly from Slav06/canopy, with individual logins, a separate live PostgreSQL database and a persistent private file disk. Existing sample data on the Mac is not uploaded. No live deployment exists until Render provisioning and post-deployment checks complete.

## Resources to review before deploying

The root render.yaml describes a Starter Node web service, Basic-256mb PostgreSQL with 1 GB storage, and a 1 GB private file disk in Ohio. These are PAID resources. Review current charges in Render before creating the Blueprint. No usage-based autoscaling is enabled. Provider bandwidth/build overages and taxes can still apply. The free Render Postgres plan expires and is unsuitable for permanent team data.

## One-time setup

1. Sign in to https://dashboard.render.com/ and select the intended workspace. Approve only the GitHub repository access needed for Slav06/canopy. If necessary, the repository owner must authorize the Render GitHub app for that repo.
2. Create a new Blueprint from https://github.com/Slav06/canopy using render.yaml. Review the selected services and costs before deployment.
3. In the secure environment-variable prompts, set BOOTSTRAP_ADMIN_EMAIL to the owner's login email and BOOTSTRAP_ADMIN_PASSWORD to a unique 14+ character password. Do not paste credentials into chat or GitHub. SESSION_SECRET is generated by Render. Database connection uses Render's private network. The database external-IP allowlist is empty.
4. Render builds the app, then runs npm run start:live. Startup derives APP_ORIGIN from Render's HTTPS URL, applies idempotent schema creation and bootstraps the first Admin before listening on Render's PORT. Existing admin accounts are never overwritten on redeploy. A database containing users without an active Admin fails startup for manual recovery rather than creating an account automatically.
5. When health checks pass, open the HTTPS service address. Confirm anonymous API access is refused, sign in as Admin and verify the live banner/empty lead list. Create individual Basic Agent or Upper Management accounts under Team and assign their leads. Agents use this same HTTPS URL and their own credentials. Remove BOOTSTRAP_ADMIN_PASSWORD from Render's environment after the first successful launch. Subsequent startup works with the existing Admin.
6. Check a second account cannot access unassigned leads, export data or delete leads. Only Admin can delete/restore. Management capabilities begin disabled. Dialerr toolbar login/permissions are separate from CRM credentials. Configure vendor-side agent permissions before calling. No Dialerr data API is used.

Automatic deploys are disabled. Pushes update GitHub, then manually deploy after review. Render's persistent disk requires one service instance and can cause brief downtime during deployment. Never scale this configuration horizontally without shared private object storage.

## Persistence and recovery

CRM records use PostgreSQL. Private documents use CRM_DATA_DIR=/var/data/canopy. The same environment setting is used by backup/restore scripts. Paid database recovery and disk snapshots are provider features; also take encrypted full CRM backups including document bytes to a separate owner-approved destination. Restore only to a fresh empty workspace, and test recovery before substantial real data entry. No external backup destination is configured automatically.

## Provider integrations

Satellite/map embeds work without setup. Mapillary remains deferred. Google Calendar sync remains optional. Keep live calling flags false until a specifically authorized test and Dialerr agent permissions have been verified; those flags do not control provider-native toolbar actions. This deployment does not import or synchronize Dialerr's lead database. Import an owner-approved CSV into the CRM and assign leads to agent accounts.

## Health and troubleshooting

/api/health is intentionally public, returning only ok/unavailable and 200/503 based on database, session secret and active Admin readiness. It never returns records. /api/state requires authentication.

If startup fails, check Render logs for missing configuration or database reachability. Do not log credentials. If adding a custom domain, set APP_ORIGIN to its exact HTTPS origin and redeploy so origin protection remains correct. Disk backups and database recovery are separate from GitHub source history.
